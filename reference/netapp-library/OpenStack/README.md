## Advanced Cinder topics
- **QoS via extra-specs**: a Cinder QoS Spec attached to a volume type creates a corresponding ONTAP QoS policy group per volume — supports non-adaptive (fixed max/min, IOPS or bytes/sec) or adaptive (paired max/min that scale with volume size) throughput control. See [ONTAP-Core QoS notes](../Networking-Performance/README.md) for the underlying ONTAP mechanism.
- **QoS policy cleanup lag**: deleting a Cinder volume does not immediately delete its associated ONTAP QoS policy group — the driver marks it for deletion and a reaping job clears it (historically on a ~60s cycle). Don't assume an orphaned-looking QoS policy group is a bug immediately after a volume delete; recheck after the reap interval before troubleshooting further.
- **Consistency groups**: NetApp's Cinder driver supports OpenStack Generic Volume Groups (from the Newton release) for ONTAP iSCSI/FC and NFS backends, enabling crash-consistent multi-volume snapshots for multi-disk applications.
- **NVMe/TCP** (recent driver generations): supports VM live migration, in-use volume expansion, multi-attach, multiple hosts per subsystem, and consistency-group snapshots — relevant for latency-sensitive database workloads moving off iSCSI/FC.
- [NetApp community: OpenStack Flamingo (2025.2) driver update detail](https://community.netapp.com/t5/Tech-ONTAP-Blogs/OpenStack-Flamingo-NetApp-Cinder-amp-Manila-Drivers-Take-a-Giant-Leap-Forward/ba-p/464590) — latest generation of both Cinder and Manila driver enhancements; treat this as the current baseline for a new deployment.

## Ceph — coexistence and comparison in mixed OpenStack estates
Many OpenStack environments run Ceph (the single most common Cinder backend across OpenStack user surveys) alongside or instead of NetApp. This is relevant when the engineer is scoping an OpenStack engagement where Ceph is already present or being evaluated against ONTAP.
- [The Implementation of OpenStack Cinder and Integration with NetApp and Ceph (research paper)](https://www.researchgate.net/publication/257925036_The_Implementation_of_OpenStack_Cinder_and_Integration_with_NetApp_and_Ceph) — documents a real mixed-backend Cinder deployment running both drivers concurrently via Cinder's multi-backend support.
- Architectural distinction: Ceph is a software-defined, scale-out distributed storage cluster (RADOS) presenting block via RBD, object via RGW (S3/Swift-compatible), and file via CephFS from the same underlying cluster — versus ONTAP's engineered, dual-controller HA array model with unified NAS/SAN/S3 from a single OS.
- **Manila**: CephFS driver vs. NetApp ONTAP driver — CephFS share deletion is asynchronous (moved to a trash folder, purged in the background) vs. ONTAP's synchronous volume delete; NetApp's driver adds enterprise features not native to CephFS out of the box, e.g. FPolicy integration (see [DSPM](../DSPM/README.md)), Barbican-backed share encryption, and `mount_point_name_support` for custom share mount naming.
- **Cinder multi-backend**: it's entirely valid to run NetApp and Ceph as separate Cinder backends in the same OpenStack deployment (e.g., Ceph for cost-sensitive bulk block, ONTAP for tiers needing SnapMirror-based DR, ONTAP QoS guarantees, or NetApp's data-reduction/dedup) — scope volume types accordingly rather than treating this as an either/or platform decision when both are already in play.
- When advising a customer already standardized on Ceph: don't position NetApp purely as a rip-and-replace — the more common and lower-risk pitch is NetApp for the workloads needing enterprise data-protection/replication guarantees (SnapMirror-based DR, ONTAP-native ransomware protection, guaranteed QoS) alongside Ceph for cost-optimized bulk capacity, using Cinder/Manila multi-backend to let both coexist under one control plane.
