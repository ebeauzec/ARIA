## AFX — disaggregated ONTAP for AI-scale workloads
- **New primary documentation hub, found 2026-07-13**: [AFX documentation](https://docs.netapp.com/us-en/ontap-afx/) — a fuller, restructured doc tree (Get started/Quick start/Install AFX hardware/Cluster administration/Manage data and access/Protect data/Secure data/REST API/FAQ) distinct from the older `ontap-technical-reports/afx-overview/` TR-style pages still linked below; both trees currently coexist on docs.netapp.com. - [Details of the AFX storage system architecture](https://docs.netapp.com/us-en/ontap-afx/get-started/software-architecture.html)
- [AFX product page](https://www.netapp.com/afx/)
- [FAQ for AFX storage systems](https://docs.netapp.com/us-en/ontap-afx/faq-ontap-afx.html)
- [NetApp AFX disaggregated storage for data-intensive AI workloads (PDF)](https://www.netapp.com/media/152362-netapp-afx-disaggregated-storage-data-intensive-ai-workloads.pdf)
- **ONTAP "personality" model (re-verified 2026-07-05 against the official FAQ)**: NetApp now formally documents three ONTAP personalities — **Unified ONTAP** (AFF/FAS/ONTAP Select/CVO, full NAS+SAN+S3), **AFX** (disaggregated, NAS/S3-only, AI/ML-focused), and **ASA r2** (disaggregated, SAN-only). A system's personality is immutable — you cannot convert or upgrade an AFF/FAS system to AFX, and you cannot mix AFX nodes with AFF/FAS/ASA nodes in the same cluster.
- **Version/interop specifics (per the official FAQ, re-verified 2026-07-05)**: AFX was announced at Insight October 2025 and supports **ONTAP 9.17.1 and later**. FlexCache to/from an AFF/FAS (Unified ONTAP) system is supported in both directions except **write-back mode**, which AFX does not support (and a FlexGroup volume on AFX cannot be a Writeback-mode FlexCache origin). For **SnapMirror or FlexCache between AFX and Unified ONTAP**, the Unified ONTAP side must be at **ONTAP 9.16.1 or later** (the release that introduced Advanced Capacity Balancing, a prerequisite for AFX interop) — don't assume an older Unified ONTAP cluster can pair with AFX without a version check. Only the **ONTAP REST API** is supported on AFX — legacy ZAPI/ONTAPI automation must be rewritten to REST before targeting an AFX cluster. AFX also drops Advanced Disk Partitioning (no root aggregates to protect) and adds NDMP alongside NFSv3/v4.x, SMB2.x/3.x, and S3 as supported data protocols.
- Architecture: **compute and storage are decoupled**, joined over a switched network, with disk ownership no longer tied to specific nodes. All capacity pools into a single **Storage Availability Zone (SAZ)** per cluster — every disk/shelf in the SAZ is available to every storage node for read/write, and all nodes participate in disk rebuilds on a failure. Only NetApp-provided/approved switches are supported for the dedicated backend cluster network (configured via a NetApp-provided file customers cannot edit) — client NFS/SMB/S3 traffic rides a separate frontend network.
- **Automated storage management**: physical aggregates are no longer exposed to the administrator — AFX automatically manages virtual capacity allocation and RAID group configuration as shelves are added. Volume balancing across nodes is handled by **Automated Topology Management (ATM)**, which detects imbalances and triggers rebalancing jobs; from **ONTAP 9.18.1**, ATM's placement algorithm became performance-aware (weighting node load, not just volume count, when placing/moving volumes) — prior AFX releases balanced purely on volume count per node regardless of activity.
- **Zero-copy data mobility**: on Unified ONTAP, moving a volume between nodes uses SnapMirror under the hood (time + temporary capacity cost); on AFX, because all nodes share the same SAZ, a **Zero Copy Volume Move (ZCVM)** relocates only the volume's metadata/pointers — no data copy required. Per the FAQ, in the initial 9.17.1 AFX release these moves are triggered only by storage-failover recovery or node add/remove events, controlled solely by ONTAP (not yet a general-purpose admin-initiated rebalancing action) — confirm current-release behavior against the FAQ before describing this as fully admin-controlled to a customer on an early AFX release.
- **Enhanced HA**: AFX removes the traditional requirement to directly cable HA partner nodes together — HA pairs communicate over the internal cluster network instead, so partners can be placed in separate racks/rows for fault tolerance. On a node failure, the failed node's volumes fail over to its HA partner to commit outstanding writes, then ONTAP rebalances volumes across all surviving nodes (not just the original two-node pair) via ZCVM.
- **Hardware components — re-confirmed unchanged via direct fetch 2026-07-13 (last checked 2026-07-07)** ([docs.netapp.com/us-en/ontap-technical-reports/afx-overview/afx-overview-hardware.html](https://docs.netapp.com/us-en/ontap-technical-reports/afx-overview/afx-overview-hardware.html), dated 2026-05-28 — supersedes the earlier press-sourced-only description): **AFX 1K controller nodes are based on the AFF A1K node hardware** (no on-board disk, 2U each, linear performance scaling as nodes are added); slot assignments are fixed — **slot 1 dedicated to HA replication, slot 7 to cluster replication, slots 10–11 to storage-shelf communication**. **NX224 shelves** reuse the same physical enclosure as AFF systems but use a different I/O module — the **NSM140** — which is what actually enables the disaggregated architecture; only **fully-populated shelves are supported** and shelves are auto-detected on connection, but **shelf removal is not currently supported**. Cluster switches are **Cisco Nexus 9332D-GX2B or 9364D-GX2A**, confirmed running **400GbE**, while node/shelf-module interfaces run 100GbE and connect via 4×100GbE breakout cables into the switch's 400GbE ports (e.g., 16×100GbE storage-shelf-module ports consume only 4 physical switch ports). **Supported NVMe SSD sizes are 7.6TB, 15.3TB, 30.1TB, and 60.6TB** — the 7.6TB/15.3TB drives are **TLC**, 30.1TB and larger are **QLC**; both meet NVIDIA SuperPOD certification performance standards for read traffic, but QLC trails TLC on write performance and shows more wear-leveling under write-heavy workloads — factor this into drive-size selection for write-intensive AI data-ingest workloads specifically, not just capacity/$/TB. **Superseded, 2026-09-07: the 7.6TB figure in this sentence is stale** — it was sourced from the retired `afx-overview-hardware.html` page; the current `afx-hardware.html` page (see the resolved disk-size discrepancy note below) confirms only 15.3TB/30.1TB/60.6TB are currently supported. - **System Manager SAZ capacity monitoring**: view Storage Availability Zone capacity details (space thresholds, snapshot consumption, data-reduction savings) and set warning/critical space-usage alert thresholds directly in System Manager.
- **Configurable QoS throughput-ceiling auto-increase**: administrators can now modify the default settings controlling automatic QoS policy-group throughput-ceiling increases in response to short-term performance needs — not modifiable in ONTAP 9.18.1 and earlier.
- **Enhanced pre-upgrade check reporting**: automated pre-upgrade checks now separate errors from warnings for easier triage before an upgrade.
- **Trident/Kubernetes REST API enhancement**: six parameters already available on the `/storage/volumes` REST endpoint were added to the `/applications/containers` endpoint, letting NetApp Trident create volumes using ONTAP's native balanced-placement capability. Cross-reference: [Kubernetes-Containers — Trident 26.06](../Kubernetes-Containers/README.md), which already documents ONTAP Balanced Placement as a Trident-side feature requiring ONTAP 9.19.1 — this is the backing REST API change.
