## How NetApp firmware updates work (architecture, not per-platform)

- **Bundled with ONTAP upgrades**: BIOS, Service Processor (SP)/BMC, disk, and disk-shelf firmware are all shipped inside the ONTAP upgrade package itself. During an ONTAP upgrade, if the firmware version already running in the cluster is older than the version bundled with the new ONTAP package, ONTAP copies the new firmware to each node's boot device and installs it automatically — BIOS updates apply at the next node boot; SP/BMC, disk, and shelf firmware update in the background, non-disruptively, during low-I/O periods after the upgrade completes. Source: [How firmware is updated during the ONTAP upgrade (KB)](https://kb.netapp.com/on-prem/ontap/Upgrade/Upgrade-KBs/How_firmware_is_updated_during_the_ONTAP_upgrade), direct-fetch-confirmed 2026-07-23.
- **Automatic Firmware Update feature (ONTAP 9.10.1+)**: lets ONTAP download and install NetApp-recommended firmware for disks, disk shelves, SP, and BMC modules **outside of** an ONTAP upgrade, over AutoSupport HTTPS connectivity — no manual intervention needed once enabled. Source: [Automatic Firmware Update feature is available starting in ONTAP 9.10.1 (KB)](https://kb.netapp.com/on-prem/ontap/Ontap_OS/OS-KBs/Automatic_Firmware_Update_feature_is_available_starting_in_ONTAP_9.10.1).
- **Manual update / status commands** (CLI, current ONTAP): `system service-processor image update` / `system service-processor image update-progress show` (SP/BMC); `storage disk firmware update` (disk); `storage shelf firmware update` (shelf/IOM); relevant auto-update toggles: `system service-processor show -fields autoupdate-enabled`, `storage disk option show -node * -fields bkg-firmware-update`, `node run -node * -command options shelf.fw.auto.update`. See [Update firmware manually](https://docs.netapp.com/us-en/ontap/update/firmware-task.html) and [Manage ONTAP SP/BMC firmware updates](https://docs.netapp.com/us-en/ontap/system-admin/methods-manage-sp-bmc-firmware-updates-concept.html).
- **Expansion cards (HBA/NIC/UTA2) — no separate firmware package exists**: NetApp does not publish standalone firmware for its HBA/NIC/UTA2 expansion cards (Qlogic/Emulex/Broadcom-based FC, FC/NVMe, iSCSI, and Ethernet adapters) — their firmware is bundled into the ONTAP upgrade package and updates the same way BIOS/SP/BMC/disk/shelf firmware does. There is consequently **no public per-card version matrix to track**; "current firmware" for an expansion card simply means "whatever ships with the node's current ONTAP release." Do not go looking for a standalone HBA/NIC firmware download on docs.netapp.com/kb.netapp.com — it doesn't exist as a customer-facing artifact the way it does for third-party HBAs used outside NetApp platforms.
- **E-Series/EF-Series is a separate world**: E-Series/EF-Series runs SANtricity (Controller Firmware 7.xx/8.xx generations), not ONTAP, and has its own firmware distribution and drive-firmware-matrix process — see the E-Series section below.

## Service Processor (SP) and Baseboard Management Controller (BMC)

**Terminology note**: "Service Processor (SP)" is NetApp's legacy remote-management term; current-generation AFF/ASA/FAS platforms use a **Baseboard Management Controller (BMC)**, which is functionally the SP's successor (remote power/console/diagnostics independent of node/ONTAP state) but versioned on its own numbering track per hardware generation — there is no single unified "BMC version" across the whole product line. See [What is a Baseboard Management Controller (BMC) and how do I use it? (KB)](https://kb.netapp.com/on-prem/ontap/OHW/OHW-KBs/What_is_a_Baseboard_Management_Controller_BMC_and_how_do_I_use_it) and [How to check the SP/BMC firmware version (KB)](https://kb.netapp.com/on-prem/ontap/hardware-KBs/How_to_check_the_SP_BMC_firmware_version).

## AFX-specific firmware update mechanism (new, added 2026-07-23, direct-fetch confirmed)

AFX storage systems use a **System Manager-driven** firmware update workflow, distinct from the CLI-centric mechanism (`system service-processor image update`, etc.) described above for AFF/FAS/ASA — confirmed via direct fetch of [Update firmware on an AFX storage system](https://docs.netapp.com/us-en/ontap-afx/administer/update-firmware.html) (contributor-dated 12/10/2025):
- **Enable/disable automatic updates**: under System Manager → Cluster → Settings → Software updates, an administrator accepts a EULA and chooses whether recommended updates for **storage firmware, SP/BMC firmware, and system files** are auto-downloaded/installed, auto-dismissed, or held for manual review via notification.
- **Manual update path**: if automatic updates are disabled, firmware files can be downloaded to a server/client and uploaded through System Manager (Cluster → Overview → All other updates → Manual Updates → Add firmware files).
- **View history**: previously-installed and pending automatic updates are both visible from the same Cluster → Settings → Software updates panel.
- **Gap**: this page confirms the *mechanism* and that AFX firmware updates cover the same storage/SP-BMC/system-file categories as AFF/FAS, but states no specific current version numbers for AFX SP/BMC or storage firmware — still no public AFX-specific entry in the BMC-by-platform-family table above; continue to treat AFX SP/BMC firmware currency as gated behind Hardware Universe/Support Site. **Re-checked 2026-09-02**: still no AFX-specific SP/BMC KB found via public search; gap unchanged. **Re-checked again 2026-09-07**: search surfaced only the same generic AFF-A250-family and BMC-mechanism results as prior passes, no AFX 1K/2K-specific SP/BMC version KB; gap remains open after three consecutive weekly checks.

## Risk & disruption notes (see [OPERATING-PROTOCOL.md](../OPERATING-PROTOCOL.md) for the full framework)

- **Routine, automatic firmware updates (BIOS at next boot, SP/BMC/disk/shelf in the background) are non-disruptive** when run through ONTAP's bundled-with-upgrade or Automatic Firmware Update mechanism with HA/redundancy intact — this is the default, recommended path.
- **Manually forcing a firmware update out of band** (`system service-processor image update`, `storage disk firmware update`, `storage shelf firmware update` run ad hoc rather than via the automatic mechanisms) is **disruptive-but-data-safe at most, and should be treated as such**: confirm no node is already in a takeover/degraded state, no shelf/loop fault already exists, and — for a shelf/IOM update specifically — that the shelf has redundant paths before starting, per the Operating Protocol's pre-condition-confirmation rule. A firmware push onto an already-degraded shelf or a controller that isn't actually HA-healthy right now is a destructive operation in disguise.
- **Asymmetric firmware across an HA pair or MetroCluster site is a real operational risk, not just a compliance nitpick**: an HA takeover/giveback or a MetroCluster switchover assumes the partner node/site can actually run the failed-over workload — a partner running materially older SP/BMC/disk/shelf firmware than the node that failed can behave unpredictably under load it wasn't validated against. Confirm firmware parity (or at least qualified-compatible versions per Hardware Universe) across an HA pair/MetroCluster site *before* relying on it for a failover, the same way the Operating Protocol requires confirming redundancy is actually intact before any disruptive operation.
- **BIOS updates require a reboot** — this is the one firmware class in this file that cannot be made fully non-disruptive on a single node; on an HA pair this is normally absorbed via takeover/giveback (disruptive-but-safe), but state this explicitly rather than letting a customer assume the whole ONTAP upgrade window will be reboot-free.
- Never present a firmware version pulled from this file as "the current, fully-qualified version for your exact platform/ONTAP release" without a Hardware Universe/Support Site check — this file exists to orient PS/SA/SAM/TAM work with public-source data, not to replace the entitlement-gated qualification check the Operating Protocol already requires for any version-sensitive recommendation.
