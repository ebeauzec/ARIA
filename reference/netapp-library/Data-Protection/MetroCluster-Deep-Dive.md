# MetroCluster Deep-Dive — All Configurations, Switch Support, Sizing, and Interoperability

Companion to the summary in [Data-Protection/README.md](README.md#metrocluster) — this file goes to the level of detail needed to actually scope, size, and configure a MetroCluster deployment. Read [OPERATING-PROTOCOL.md](../OPERATING-PROTOCOL.md) first: several operations referenced here (switchover, expansion, ONTAP upgrade on a 4-/8-node system) are disruptive-but-safe only when their pre-conditions are verified, and this document flags those points inline.

**Authoritative source of truth for anything version/firmware-specific**: the NetApp Interoperability Matrix Tool (IMT) (support login required) — select the MetroCluster solution type under "Storage Solution" and use Component Explorer to pin ONTAP version, switch model, and firmware. Only IMT/Hardware Universe-listed combinations are supported; every distance/latency figure below is a general-planning number, not a substitute for an IMT check on the specific customer configuration. See [Using the IMT to find MetroCluster information](https://docs.netapp.com/us-en/ontap-metrocluster/maintain/concept_using_the_interoperability_matrix_tool_to_find_mcc_information.html).

## Configuration types (current and legacy)

### Stretch MetroCluster (shortest distance, simplest, legacy-leaning)
- No FC switches or ATTO bridges: controllers cable **directly** to disk shelves at both sites using NetApp proprietary long-reach SAS cables (direct-attach variant), or via **FC-to-SAS bridges** (ATTO FibreBridge 7500N/7600N) where SAS shelves are daisy-chained behind the bridge (bridge variant, used when disk shelves are further from the controller than direct SAS reach allows).
- [Install a stretch MetroCluster configuration (PDF)](https://docs.netapp.com/us-en/ontap-metrocluster/pdfs/sidebar/Install_a_stretch_MetroCluster_configuration.pdf)
- [Configure FC-to-SAS bridges](https://docs.netapp.com/us-en/ontap-metrocluster/install-stretch/task_configure_the_fc_to_sas_bridges_fb_new_install_configure.html) · [Install FC-to-SAS bridges and SAS disk shelves](https://docs.netapp.com/us-en/ontap-metrocluster/install-stretch/task_fb_new_install.html) · [Map SAS cabling in an ATTO FibreBridge configuration (KB)](https://kb.netapp.com/Advice_and_Troubleshooting/Data_Protection_and_Security/MetroCluster/How_to_map_SAS_cabling_in_an_ATTO_FibreBridge_based_configuration)
- ATTO FibreBridge models: **7600N** (up to 32/16/8 Gbps) and **7500N** (up to 16/8/4 Gbps) — match bridge speed to the FC HBA and switch/port speed actually provisioned, not just the bridge's rated maximum.
- Distance: SAS cable reach limits stretch configurations to roughly 270–500m between sites depending on cable type/generation (sources vary in this range — treat 300m as a conservative planning ceiling and confirm the exact supported distance for the specific cable/shelf combination via IMT/Hardware Universe). This is a same-building/same-campus solution, not a metro-DR solution.
- Bridge monitoring: ONTAP 9.8+ monitors FC-to-SAS bridges via **in-band connections by default** — no extra monitoring configuration needed. Pre-9.8, bridges require separate/explicit monitoring setup — a materially different operational posture if a customer is still on an older release.
- Positioning: stretch is effectively a **legacy/niche** configuration for new designs — it protects against a rack or single-room failure, not a site-level disaster. For genuine site-level DR, use Fabric-Attached FC or MetroCluster IP instead.

### Fabric-Attached MetroCluster (FC)
- [MetroCluster documentation hub](https://docs.netapp.com/us-en/ontap-metrocluster/) · [Configure MetroCluster FC software in ONTAP](https://docs.netapp.com/us-en/ontap-metrocluster/install-fc/concept_configure_the_mcc_software_in_ontap.html)
- Uses FC switches (Brocade or Cisco) and, where SAS shelves are used, ATTO FC-to-SAS bridges, to connect the two sites over metro-scale distances.
- **Switch vendor support**: both **Brocade** and **Cisco** FC switches are supported — but per-fabric port numbering conventions differ (Brocade starts at port 0, Cisco starts at port 1), which matters when following a cabling diagram literally. [Configuring Cisco FC switches manually](https://docs.netapp.com/us-en/ontap-metrocluster/install-fc/task_fcsw_cisco_configure_a_cisco_switch_supertask.html) · [Firmware versions supported for Brocade/Cisco switches in a MetroCluster (KB)](https://kb.netapp.com/on-prem/ontap/mc/MC-KBs/What_versions_of_Brocade_Cisco_switch_firmware_can_be_used_in_a_MetroCluster) — this KB (and the IMT) is the only authoritative source for which specific firmware builds are qualified; firmware qualification changes over time independent of ONTAP releases.
- **Distance**: **300 km (185 miles)** maximum specifically when using **Brocade 6505 or 6510** switches; **200 km (120 miles)** maximum for all other supported FC/FCIP switch combinations. Don't assume the 300km figure applies to a Cisco-switch design — confirm the actual qualified distance for the specific switch model via IMT.
  - **Verification status (checked 2026-08-10)**: direct-fetched [TR-4705 (Solution architecture and design)](https://www.netapp.com/media/13480-tr4705.pdf) — NetApp's own current architecture reference — and it states only a **blanket "up to 300km for FC"** figure (pp. covering ISL distances and the FC section), with no Brocade-vs-Cisco split stated in that document. Could not locate the specific **200km (non-Brocade)** figure in any current, directly-fetchable docs.netapp.com or netapp.com primary source this pass — the only supporting sources found were a community.netapp.com forum thread and an older MetroCluster FC FAQ PDF, neither of which is the current authoritative reference. NetApp's own current guidance (repeated across the FC install docs) is that exact max distance is **switch-model-and-RTT dependent and must be confirmed per the Interoperability Matrix Tool / Hardware Universe** rather than treated as a fixed number — so treat 300km as reasonably well-supported (two independent primary sources) and **200km as unconfirmed by current primary source**, not as verified fact, until checked against IMT/HWU for the specific switch model in play.
- **Node counts**: 4-node fabric-attached MetroCluster FC is the standard current building block; can be **expanded from 2-node to 4-node**, and **4-node to 8-node**, as separate documented procedures (see Expansion section below) — these are not simple reconfigurations, they're structured, version-gated procedures.
- Switch ports required scales with node count — see [switch ports required for an 8-node MCC configuration with array LUNs](https://docs.netapp.com/us-en/ontap-metrocluster/install-fc/concept_switch_ports_required_for_a_eight_node_mcc_configuration_with_array_luns.html) for the array-LUN-specific case.
- TR-4705 (solution architecture/design) and TR-4375 (MetroCluster FC specifics) are the primary design references — see [Data-Protection/README.md](README.md#metrocluster) for links.

### MetroCluster IP
- [MetroCluster IP install documentation](https://docs.netapp.com/us-en/ontap-metrocluster/install-ip/) · [Required MetroCluster IP components and naming conventions](https://docs.netapp.com/us-en/ontap-metrocluster/install-ip/concept_required_mcc_ip_components_and_naming_guidelines_mcc_ip.html)
- Uses Ethernet/IP inter-switch links instead of FC ISLs — both NVRAM mirroring and SyncMirror replication ride over high-speed Ethernet. This is the current, NetApp-preferred architecture for new metro-DR designs (simpler operationally than maintaining a separate FC fabric purely for MetroCluster).
- **Switch options — two distinct tiers, verified against the primary doc 2026-07-04**:
  - **NetApp-validated switches**: provided by NetApp as part of the MetroCluster IP configuration, listed in the [NetApp Hardware Universe](https://hwu.netapp.com/) under "MetroCluster-over-IP-connections" (historically including Broadcom/Brocade **BES-53248** — see [platform port assignments for BES-53248](https://docs.netapp.com/us-en/ontap-metrocluster/install-ip/port_usage_bes53248.html)), used *only* to connect MetroCluster IP controllers (and in some configs, NS224 shelves), and configured via NetApp's own Reference Configuration File (RCF). Full support, no functional limitations.
  - **MetroCluster-compliant switches** (from ONTAP 9.7+): **not** NetApp-validated, but usable if they meet a defined requirement set — QoS/traffic classification, ECN, a load-balancing policy that preserves packet order, L2 Flow Control, a dedicated (non-oversubscribed) port rate, NetApp-provided/switch-vendor-supported cables and transceivers, and MTU 9216 on every switch carrying MetroCluster IP traffic. **NetApp does not provide troubleshooting or configuration support for these switches** — that support gap is a real operational cost to disclose, not a footnote. See [full requirements and limitations](https://docs.netapp.com/us-en/ontap-metrocluster/install-ip/concept-requirement-and-limitations-mcc-compliant-switches.html).
  - **Hard limitations specific to MetroCluster-compliant (non-validated) switches** — do not scope any of the following against a compliant-switch design: **8-node MetroCluster IP configurations**, **FC-to-IP transition**, **refreshing a 4-node MetroCluster IP configuration**, or platforms that share a physical interface between local-cluster and MetroCluster traffic (check [platform-specific network speeds/switch-port modes](https://docs.netapp.com/us-en/ontap-metrocluster/install-ip/concept-network-speeds-and-switchport-modes.html) for which platforms that affects). A compliant-switch MetroCluster-compliant switch also **cannot be shared with local cluster interconnect traffic** and requires **four IP switches** (two per fabric; a single director per side is acceptable only if MetroCluster IP interfaces land on two different blades in two different failure domains on that director) — each node's MetroCluster interfaces must connect to two different switches/blades, never the same one twice.
  - Running MetroCluster IP over a customer's existing shared L2/L3 network (rather than a MetroCluster-dedicated switch pair) is explicitly supported subject to the same compliant-switch requirements plus additional network-specific rules — see [Requirements to deploy MetroCluster IP in shared L2/L3 networks](https://docs.netapp.com/us-en/ontap-metrocluster/install-ip/concept-considerations-layer-2-layer-3.html). **Design implication**: if a customer wants to run MetroCluster IP over their existing network fabric to avoid a dedicated switch purchase, that choice forecloses 8-node scale, FC-to-IP transition, and 4-node refresh procedures later — confirm this tradeoff is acceptable for their growth plan before recommending the shared-network path purely on cost grounds.
  - Reverting a MetroCluster-compliant-switch configuration to ONTAP 9.6 or earlier is **not supported** — factor this into any downgrade contingency planning.
- **Distance**: up to **700 km** for the 4-node MetroCluster IP solution — the most distance-flexible of the three configuration types.
- **Node counts**: 4-node is standard; **8-node support added in ONTAP 9.9.1** for MetroCluster IP specifically (fabric-attached FC reached 8-node earlier, under ONTAP 9). 4- and 8-node configurations in general require **ONTAP 9.8 or later** — do not attempt the documented upgrade procedures against a 4-/8-node system running an older release.
- Cables/transceivers connecting nodes to switches must be **NetApp-provided and switch-vendor supported** — this is a hard requirement, not a recommendation; using third-party optics not qualified for the switch can produce intermittent, hard-to-diagnose ISL errors.

## ISL (Inter-Switch Link) requirements — MetroCluster IP
Full detail: [ISL requirements overview](https://docs.netapp.com/us-en/ontap-metrocluster/install-ip/overview-isl-requirements.html) · [Requirements for ISLs](https://docs.netapp.com/us-en/ontap-metrocluster/install-ip/concept-requirements-isls.html) · [ISL considerations](https://docs.netapp.com/us-en/ontap-metrocluster/install-ip/concept_considerations_isls.html)

- **Packet loss**: must be ≤ 0.01%.
- **Jitter**: ≤ 3ms round-trip (≤ 1.5ms one-way).
- **Fabric distance symmetry**: the maximum supported *difference* in distance between fabric 1 and fabric 2 is **20 km or 0.2ms** — an asymmetric dual-path design outside this tolerance is not supported, not just suboptimal.
- **Minimum ISL count/speed**: at least one 10Gbps ISL port per fabric on most platforms; **from ONTAP 9.18.1**, platforms whose MetroCluster IP backend port speed is 100Gbps require a **minimum 100Gbps ISL** — confirm which regime applies to the target platform/ONTAP version combination before sizing WAN circuits.
- **Latency rule of thumb**: round-trip latency increases roughly **1ms per 100km** of distance — use this only for first-pass planning; the actual qualifying factor is the jitter/packet-loss/distance-symmetry requirements above, not raw latency alone.
- **Sizing implication**: a WAN circuit that "looks" adequate on raw bandwidth can still fail MetroCluster IP qualification on jitter or packet-loss grounds — treat carrier SLA numbers for jitter/loss as a hard gating requirement during design, not a nice-to-have, and get them in writing before committing to a distance/circuit combination.

## Tiebreaker vs. ONTAP Mediator
Full detail: [Differences between ONTAP Mediator and MetroCluster Tiebreaker](https://docs.netapp.com/us-en/ontap-metrocluster/install-ip/concept_considerations_mediator.html) · [Set up Tiebreaker or Mediator](https://docs.netapp.com/us-en/ontap-metrocluster/install-ip/task_sw_config_configure_mediator.html) · [MetroCluster Tiebreaker installation and configuration guide](https://docs.netapp.com/us-en/ontap-metrocluster/tiebreaker/) · [ONTAP Mediator installation requirements](https://docs.netapp.com/us-en/ontap-metrocluster/install-ip/concept_mediator_requirements.html)

- **MetroCluster Tiebreaker**: third-party software installed on a Linux host at a *third site*, monitors reachability of both clusters and inter-cluster connectivity to detect a site failure. Can monitor **up to 15 MetroCluster configurations simultaneously**, and supports a **mix of MetroCluster IP, FC, and Stretch** configurations from one Tiebreaker instance — the only option if the estate includes non-IP MetroCluster types or needs single-pane monitoring across many MetroCluster pairs.
- **ONTAP Mediator**: built into ONTAP from 9.7+, also runs on a third-site Linux host, but is **IP-configuration-only** and enables **MAUSO (Mediator-Assisted automatic Unplanned SwitchOver)** — fully automatic switchover on a detected site failure, without a human triggering it.
- **Mediator scale and protocol (ONTAP 9.18.1+/9.19.1)** — per [Mediator installation requirements](https://docs.netapp.com/us-en/ontap-metrocluster/install-ip/concept_mediator_requirements.html) (07/17/2026) and [What's new in ONTAP Mediator support for MetroCluster IP](https://docs.netapp.com/us-en/ontap-metrocluster/releasenotes/mcc-mediator-whats-new.html) (07/15/2026), verified 2026-10-08:
  - **iSCSI** (default): up to **10** MetroCluster configurations per instance from ONTAP 9.18.1 / Mediator 1.11 (5 with 9.17.1 / Mediator 1.10 and earlier).
  - **HTTPS** (ONTAP 9.19.1 / Mediator 1.12+, CLI only, encrypts the whole session): Mediator **1.12** = 1 configuration. Mediator **1.12.1+** = **10 four-node or 5 eight-node** configurations on a host with at least 8 CPU cores and 16 GB RAM, and 1 on a smaller host. A 1.12.1+ HTTPS instance can also monitor **one four-node MetroCluster IP plus one SnapMirror active sync peer relationship**.
  - An instance uses iSCSI or HTTPS, never both. Going beyond the HTTPS limits is not supported.
  - **Risk note (classify: disruptive-safe at most, plan it as a change)**: moving an existing Mediator from iSCSI to HTTPS, or adding configurations to one instance, changes what MAUSO depends on. Before the change, confirm MetroCluster health (`metrocluster check run`, then `metrocluster check show`) and that the Mediator connection is up. Size the host first: a sub-8-core HTTPS host is limited to one configuration. Rollback: keep the old Mediator configuration details so you can remove and re-add the Mediator with the previous protocol if the new connection does not come up.
- **Mutual exclusivity**: you **cannot run both** Tiebreaker and ONTAP Mediator against the same MetroCluster configuration — pick one per configuration. Tiebreaker for FC/Stretch or multi-configuration monitoring estates; Mediator for a pure-IP configuration wanting automatic (not just alerted) switchover.
- **Risk note**: MAUSO means an unplanned switchover can execute **without human confirmation** the moment the Mediator's failure-detection criteria are met — before enabling it, make certain the customer understands and accepts that an automatic site failover is now a possible unattended outcome of a detected network partition or site outage, not just an alert. This is a design decision with real operational-risk tradeoffs (faster RTO vs. risk of a false-positive automatic failover), not a default to enable without discussion, per the [Operating Protocol](../OPERATING-PROTOCOL.md).

## ONTAP version support matrix (general — confirm exact figures via IMT)
- **2-node MetroCluster FC**: added in Data ONTAP 8.3.1. Now considered a legacy topology for new designs — NetApp's current guidance steers new deployments toward 4-node FC or MetroCluster IP; a 2-node design has no non-disruptive expansion path to add local HA at either site without a documented 2-node→4-node expansion project.
- **4-node MetroCluster (FC)**: available since Data ONTAP 8.3.0; remains a fully current, supported topology.
- **8-node MetroCluster FC**: supported from ONTAP 9 (fabric-attached).
- **8-node MetroCluster IP**: supported from **ONTAP 9.9.1**.
- **4-/8-node configurations generally**: require **ONTAP 9.8 or later** for the documented expansion/upgrade procedures — do not run those procedures against an older release without a version upgrade first.
- **Expansion/upgrade rule**: old and new nodes being combined in an expansion **must run the same ONTAP version** — a mixed-version expansion is not a supported intermediate state, it's a precondition failure.
- **FC-to-IP transition**: NetApp documents a defined (disruptive) procedure for migrating an existing FC-based MetroCluster to IP — see [Preparing for disruptive FC-to-IP transition](https://docs.netapp.com/us-en/ontap-metrocluster/transition/concept_requirements_for_fc_to_ip_transition_2n_mcc_transition.html). Treat this as a planned-maintenance-window project, not an in-place reconfiguration — the name says it plainly: disruptive.

## Best-practice summary (cross-referencing the rest of the library)
- Always start design/sizing from the NetApp Interoperability Matrix Tool for the specific ONTAP version, switch model/firmware, and distance/latency the customer's WAN circuit actually delivers — every distance/latency number in this document is a planning approximation, and the IMT is what gets qualified/supported status right.
- Match the MetroCluster type to the actual DR requirement: Stretch for same-site/same-building resilience only; Fabric-Attached FC where an existing FC switch estate and skillset already exists and 200–300km covers the requirement; MetroCluster IP for new designs, longer distances (up to 700km), or where avoiding a dedicated FC fabric is a design goal.
- Never mix FC switch vendors within a single fabric; confirm port-numbering convention (Brocade 0-based, Cisco 1-based) before following a generic cabling diagram literally.
- Size the WAn circuit against the jitter/packet-loss/distance-symmetry ISL requirements, not just raw bandwidth or the 1ms/100km latency rule of thumb.
- Pick Tiebreaker vs. Mediator deliberately — Mediator's MAUSO capability trades faster automatic recovery for the operational risk of an unattended automatic switchover; make sure that tradeoff is a documented decision, not a default.
- Cross-reference [Host-Integration-Cabling](../Host-Integration-Cabling/README.md) for the physical per-platform cabling guides and [Platforms-Hardware](../Platforms-Hardware/README.md) for current vs. legacy controller platform context when scoping a MetroCluster refresh or expansion.
