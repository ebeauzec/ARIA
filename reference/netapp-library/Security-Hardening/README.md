## Ransomware protection
- [ONTAP Autonomous Ransomware Protection (ARP) — overview](https://docs.netapp.com/us-en/ontap/anti-ransomware/)
- [ARP use cases and considerations](https://docs.netapp.com/us-en/ontap/anti-ransomware/use-cases-restrictions-concept.html)
- [Enable ARP on a volume](https://docs.netapp.com/us-en/ontap/anti-ransomware/enable-task.html) / [Enable ARP by default on new volumes](https://docs.netapp.com/us-en/ontap/anti-ransomware/enable-default-task.html)
- [Learn about NetApp Ransomware Resilience (managed service)](https://docs.netapp.com/us-en/data-services-ransomware-resilience/concept-ransomware-resilience.html)
- **NetApp–Elastio partnership (newly documented this refresh — announced 2026-03-24, previously missed in this library)**: [NetApp and Elastio Announce Partnership to Deliver Defense-in-Depth Ransomware Resilience (press release)](https://www.netapp.com/newsroom/press-releases/news-rel-20260324-609577/) · [Elastio for NetApp](https://elastio.com/platform/netapp/). Embeds **Elastio Provable Recovery Control** — deep, file-level inspection of ONTAP snapshots that detects zero-day ransomware, staged malware, and stealth corruption that evaded perimeter/behavioral controls, and continuously identifies the last known-clean recovery point — directly into the [NetApp Ransomware Resilience managed service](https://docs.netapp.com/us-en/data-services-ransomware-resilience/concept-ransomware-resilience.html) above, with no separate procurement or architecture change for the customer. This is a *second, deeper* detection layer behind ARP (which watches live I/O) and behind the backup-vendor DSPM/threat-detection layer (see [Backup-3rdParty](../Backup-3rdParty/README.md#advanced-vendor-capabilities-2026)) — Elastio inspects the snapshot content itself for dormant/staged threats that neither ARP's in-line behavioral analysis nor a backup vendor's access-pattern monitoring would necessarily catch. **Status as of this check**: announced/roadmap-stage, not yet broadly GA — planned availability starts with **Amazon FSx for NetApp ONTAP**, followed by other ONTAP environments; confirm current productization/entitlement status before scoping a customer design around this specifically — same roadmap-stage caveat as the [NetApp–Commvault Closed-Loop Recovery Architecture](../Backup-3rdParty/README.md#advanced-vendor-capabilities-2026), announced the same day (2026-03-24).
- Mechanism: available from ONTAP 9.10.1, ARP performs real-time NAS (NFS/SMB) workload analysis, detects anomalous encryption-pattern activity after only a small number of files are affected, and automatically creates a locked snapshot for recovery while alerting administrators.
- Rollout best practice: run ARP in **learning mode** for a minimum of 30 days (ONTAP 9.10.1–9.15.1) before switching to active enforcement, to avoid false positives against legitimate workload behavior.
- **ARP/AI — the machine-learning model, added to this library 2026-07-31 (direct-fetch confirmed against [Learn about ONTAP Autonomous Ransomware Protection](https://docs.netapp.com/us-en/ontap/anti-ransomware/), page contributor-dated 07/07/2026)**: beginning with **ONTAP 9.16.1**, ARP adopts an AI/machine-learning detection model (pre-trained off-box on forensic ransomware datasets, not on customer data; shipped on-box, not editable via CLI/API) claimed to detect ransomware with **99% accuracy in NAS environments**. This supersedes the "run learning mode for 30 days" guidance above for anything on ARP/AI-supported versions/volume types — **there is no learning period; ARP/AI is active immediately** on: NAS FlexVol (9.16.1+), NAS FlexGroup (9.18.1+), and SAN volumes (9.17.1+, active during the still-required 2–4 week baseline *evaluation* period rather than a passive learning period). Pre-9.16.1 FlexVol and 9.13.1–9.17.1 FlexGroup volumes still run the older entropy/extension/IOPS model and still need the 30-day learning-mode guidance above.
  - **Default enablement moved from opt-in to opt-out over two releases**: **ONTAP 9.18.1** turned ARP on **by default on all new volumes** for AFF A-series/C-series, ASA, and ASA r2 systems (customers can opt out at the cluster level during a grace period). **ONTAP 9.19.1** extended that default enablement to clusters using SnapMirror synchronous/active sync SAN relationships (suppressed for those configs in 9.18.1) — cross-reference the AFX/SnapMirror-synchronous ARP note above, but note **ARP is explicitly not enabled by default on AFX** even with SnapMirror synchronous support.
  - **Scope and upgrade behavior, confirmed 2026-09-17 via direct fetch of the core [What's new in ONTAP 9.19.1](https://docs.netapp.com/us-en/ontap/release-notes/whats-new-9191.html) page** (page itself unchanged since 07/28/2026 — this closes a library gap, not a new release): ARP/AI protects primary volumes in **SnapMirror synchronous (both NAS and SAN)** relationships on **FAS, AFF, and AFX** systems, and in **SnapMirror active sync SAN** relationships on **AFF and ASA r2** systems specifically — detection always runs on the active read-write primary, where ARP/AI snapshots are created (they are not replicated to the secondary, consistent with the SnapMirror-sync caveat already noted above). **Upgrade behavior**: a cluster upgraded to ONTAP 9.19.1 that previously had default ARP/AI enablement *suppressed* because of a synchronous-replication relationship will have that default enablement **automatically restored** on upgrade — a pre-update warning notifies administrators and gives them the option to disable it before the restore takes effect. Factor this into any 9.19.1 upgrade plan for a customer running SnapMirror synchronous/active sync today with ARP/AI intentionally disabled — the upgrade will silently re-enable it unless the warning is acted on.
  - **Practical effect for a customer conversation**: on a cluster already at 9.16.1+, don't default to recommending a 30-day learning-mode wait before treating ARP as fully protective — check which model (ARP vs. ARP/AI) and which enablement default actually applies to the target ONTAP version/volume type/platform first.
- **Page restructure and new granular detail, found 2026-08-08 (direct-fetch of [Learn about ONTAP Autonomous Ransomware Protection](https://docs.netapp.com/us-en/ontap/anti-ransomware/), now contributor-dated 08/06/2026, up from 07/07/2026)**: the landing page has split into two version-specific pages — [ARP/AI (ONTAP 9.16.1 and later)](https://docs.netapp.com/us-en/ontap/anti-ransomware/learn-about-arpai.html) and [ARP (ONTAP 9.10.1–9.15.1)](https://docs.netapp.com/us-en/ontap/anti-ransomware/learn-about-arp.html) — confirm which one applies before citing behavior. New facts confirmed on the page (quoted): the legacy ARP model "received no new functional improvements after ONTAP 9.14.1." A new comparison table adds detail not previously in this library:
  - **ARP/AI snapshot behavior**: snapshots are "created at fixed 4-hour intervals and on attack confirmation" (vs. legacy ARP, which snapshots only on a trigger — high entropy, new file extension, or file-operation surge). Default retention for ARP/AI snapshots is **12 hours**, extended to **24 hours on a confirmed false positive** and **7 days on a confirmed attack**.
  - **ARP/AI gets "automatic security updates independent of ONTAP releases"** — the detection model itself can update out-of-band from an ONTAP upgrade, unlike legacy ARP's static, ONTAP-upgrade-only detection logic.
  - **Evaluation-period scope widened**: beyond the existing 2–4 week SAN evaluation period, ONTAP 9.17.1 also requires an evaluation period for **NAS FlexVol volumes with ONTAP-detected hypervisor virtual disks** — a new case to flag when scoping ARP/AI against a NAS datastore hosting VM disks.
  - **Licensing (new to this library)**: ARP is included with the **ONTAP One** license. Without ONTAP One: ONTAP 9.11.1+ requires the `Anti_ransomware` license; ONTAP 9.10.1 uses `MT_EK_MGMT` (Multi-Tenant Key Management) instead. Upgrading 9.10.1→9.11.1+ with ARP already configured does not require re-licensing; new configurations do. Reverting from 9.11.1+ (licensed under `Anti_ransomware`) back to 9.10.1 triggers a warning and possible reconfiguration.
- **ARP feature-by-release page, added 2026-10-08 (direct-fetch confirmed)**: [ONTAP Autonomous Ransomware Protection feature availability by release](https://docs.netapp.com/us-en/ontap/anti-ransomware/release-history-arp.html) (dated 09/08/2026) is now the single page that lists ARP changes per ONTAP release, 9.10.1 through 9.19.1. Use it first when you scope ARP for a customer's version. Two items it states that this README did not yet carry:
  - **Hypervisor coverage**: ARP/AI supports NAS volumes that hold VMware vSphere virtual disks from 9.17.1. **From ONTAP 9.17.1P5, it also supports Hyper-V, KVM, and OpenStack hypervisors.** This is a P-release floor, so check the exact patch level, not only the 9.17.1 major.
  - **ONTAP 9.18.1 System Manager change**: System Manager no longer shows ARP/AI workload characteristics (baseline and surge statistics), because users often misread surge activity as an attack. Detection does not change. The statistics stay available in the CLI and REST API. Do not tell a 9.18.1+ customer to "check the surge graph in System Manager".
- Pair ARP with Multi-Admin Verification (below) so a single compromised admin credential can't disable protection or dismiss a real attack as a false positive.
- **Risk note**: `security anti-ransomware volume disable`/`pause` and marking a suspected attack a false positive are protection-*reducing* actions — treat them as destructive-tier under the [Operating Protocol](../OPERATING-PROTOCOL.md) even though they don't delete data directly, because they remove the safety net during exactly the window an attack might be active. Never recommend disabling/pausing ARP as a troubleshooting shortcut (e.g., to stop alert noise) without confirming there is no genuine active-attack indicator first, and confirm MAV approval is factored into the timeline.

## Multi-Admin Verification (MAV)
- [Learn about ONTAP multi-admin verification](https://docs.netapp.com/us-en/ontap/multi-admin-verify/)
- [Enable/disable MAV](https://docs.netapp.com/us-en/ontap/multi-admin-verify/enable-disable-task.html) · [Manage approval groups](https://docs.netapp.com/us-en/ontap/multi-admin-verify/manage-groups-task.html) · [Manage protected-operation rules](https://docs.netapp.com/us-en/ontap/multi-admin-verify/manage-rules-task.html) · [Manage MAV requests](https://docs.netapp.com/us-en/ontap/multi-admin-verify/manage-requests-task.html)
- Available from ONTAP 9.11.1 (protected operations generally); ONTAP 9.13.1+ extends MAV specifically to ARP disable/pause/false-positive actions.
- Caveat: MAV is not designed for heavily automated workflows — every protected operation requires human approval, so scope MAV rules narrowly (e.g., volume/snapshot deletion, ARP overrides) rather than broadly, or automation pipelines will stall waiting on approval.
- **Full per-release protected-command matrix, direct-fetch confirmed 2026-08-10, re-confirmed unchanged 2026-08-17** (page still contributor-dated 07/13/2026): the concept page publishes a complete, version-pinned list of rule-protected commands from 9.11.1 through the current 9.19.1, each release's additions footnoted to the release that introduced them. This is the authoritative source for "is command X MAV-protectable on version Y" — don't infer from the 9.19.1 list alone for an older cluster.
  - **System-defined guard-rail rules** (present on every MAV-enabled cluster, cannot be removed): `security multi-admin-verify modify`, `security multi-admin-verify approval-group *`, `security multi-admin-verify rule *`, `security multi-admin-verify request *` — these protect the MAV mechanism itself from being circumvented.
  - **New in 9.19.1** (not available for MAV protection on earlier releases): a large block of QoS commands (`qos adaptive-policy-group`/`qos policy-group`/`qos settings`/`qos workload` create/modify/delete/rename), `security dynamic-authorization modify`, `security key-manager external gcp disable`, `placement rebalance performance config modify`, and `vserver consistency-group snapshot rename`.
  - **Structural note**: MAV rules are evaluated *after* RBAC — an administrator must already hold the RBAC privilege for an operation before a MAV rule can require a second approver; MAV is a second gate, not a replacement for RBAC scoping.
  - **Cross-reference**: this per-version list is the basis for scoping which destructive/irreversible commands from the [Operating Protocol](../OPERATING-PROTOCOL.md) classification a given customer's ONTAP version can actually MAV-protect — confirm against this table before promising MAV coverage for a specific command on an older cluster.
- **Risk note**: disabling MAV itself, or removing rules/approval-group members, is a **destructive-tier control change** even though it deletes no data — it removes the guard-rail that prevents a single compromised or mistaken administrator from executing the destructive commands listed in [ONTAP-Core](../ONTAP-Core/README.md#risk--disruption-notes-applies-across-all-ontap-cli-guidance--see-operating-protocolmd). If MAV genuinely needs to be disabled (e.g., the sole MAV admin is unavailable), route through NetApp Support per the documented process rather than a workaround — see the note on the MAV concept page above.

## Encryption at rest
- [NetApp Volume/Aggregate Encryption — concept](https://docs.netapp.com/us-en/ontap/encryption-at-rest/configure-netapp-volume-encryption-concept.html)
- [Enable NAE or NVE on an existing volume](https://docs.netapp.com/us-en/ontap/encryption-at-rest/encrypt-existing-volume-task.html)
- [Storage encryption in ONTAP (hardening-guide chapter)](https://docs.netapp.com/us-en/ontap-technical-reports/ontap-security-hardening/storage-encryption.html)
- Three mechanisms: **NVE** (NetApp Volume Encryption, software, XTS-AES-256, one key per volume, excluded from aggregate-level dedupe), **NAE** (NetApp Aggregate Encryption, ONTAP 9.6+, shared aggregate-level key, volumes remain eligible for aggregate dedupe), **NSE** (NetApp Storage Encryption, hardware self-encrypting drives).
- Default behavior since ONTAP 9.7: new aggregates get NAE by default and new volumes outside an NAE aggregate get NVE by default, provided a volume-encryption license and a key manager (onboard or external) are configured.
- Key management: use external KMIP-compliant key servers when FIPS 140-2/OASIS KMIP compliance or multi-cluster centralized key management is required; otherwise the Onboard Key Manager is sufficient — best practice is to host external key servers on infrastructure separate from the data they protect.
- **Risk note**: `storage encryption disk destroy`/`sanitize`/`revert-to-original-state` are **irreversible data-destruction operations** by design (that's their purpose for decommissioning) — never present these in response to a routine encryption question; they belong only in a deliberate, confirmed decommission/disposal workflow. Losing or failing to back up an onboard/external encryption key is equally irreversible (data becomes permanently unreadable) — any key-manager migration or passphrase-rotation recommendation must include a verified key-backup step before the change, not after.

## Remediation workflow (general pattern)
1. Confirm scope via ARP snapshot/alert or AutoSupport/Active IQ Digital Advisor finding (see [Operations-Troubleshooting](../Operations-Troubleshooting/README.md)).
2. Isolate the affected SVM/volume (network segmentation or export-policy lockdown) before making any recovery changes.
3. Recover from the last known-good ARP-locked snapshot or SnapMirror/SnapVault copy rather than the live volume.
4. Review MAV logs and approval-group membership for signs of credential compromise; rotate keys/credentials as needed.
5. File/update an AutoSupport case referencing the incident for NetApp Support visibility if it's a suspected active exploit, not just a policy drill.
