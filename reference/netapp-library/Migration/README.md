# Migration — Homogeneous & Heterogeneous, Storage-Based & Application-Based

Framework: migrations split along two independent axes — **homogeneous** (NetApp-to-NetApp) vs. **heterogeneous** (3rd-party array/NAS-to-NetApp), and **storage-based** (block/LUN or NAS/file level, application-unaware) vs. **application-based** (VM, database, container — application-aware, often using storage-based tools underneath). Use this README to pick the right tool, then follow the linked procedure. All migration cutovers are evaluated under the [Operating Protocol](../OPERATING-PROTOCOL.md) — see the risk notes at the end of each section.

## Storage-based, homogeneous (NetApp → NetApp)

- **`volume move`** — intra-cluster relocation of a FlexVol between aggregates/nodes. [Move an ONTAP volume](https://docs.netapp.com/us-en/ontap-sm-classic/online-help-96-97/task_moving_flexvol_volumes_between_aggregates_or_nodes.html). Non-disruptive; works even on a volume that is the source or destination of an active SnapMirror/SnapVault relationship — you do **not** need to break the mirror first. SnapMirror updates pause briefly only during the final cutover phase and resume automatically afterward. Use this for node decommission, aggregate rebalancing, or QoS/tier relocation within a cluster.
- **SnapMirror-based cross-cluster migration** — cluster-peer two clusters, establish a SnapMirror relationship for the volumes to be moved, let it sync, then cut over (break/resync or a planned LIF/namespace cutover depending on protocol). This is the standard homogeneous cross-cluster/cross-site migration pattern and is exactly the SnapMirror mechanism documented in [Data-Protection](../Data-Protection/README.md) — migration is simply "SnapMirror with an intent to cut over," not a separate tool.
- **7-Mode Transition Tool (7MTT)** — legacy but still relevant wherever 7-Mode systems remain in the field. [7-Mode Transition documentation hub](https://docs.netapp.com/us-en/ontap-7mode-transition/) · [7MTT process (KB)](https://kb.netapp.com/Legacy/ONTAP/7Mode/7MTT_Process) · [7-Mode Transition Tool 3.3.1 Copy-Based Transition Guide (PDF)](https://library.netapp.com/ecm/ecm_download_file/ECMLP2843879)
  - **Copy-Based Transition**: volume-level SnapMirror-based replication from 7-Mode to clustered ONTAP (cDOT), supports both NAS and SAN configurations, and — because it rides on SnapMirror — preserves existing SnapMirror relationships, Snapshot copies, and storage-efficiency settings across the transition.
  - **Copy-Free Transition**: an alternative, faster path (no data copy) for specific supported configurations — check current 7MTT documentation for exact eligibility, as Copy-Free Transition has narrower hardware/config prerequisites than Copy-Based.
  - **Status note**: 7-Mode has been out of NetApp's mainstream support focus for years; if a customer still has 7-Mode in production, treat this as an overdue, EOS-adjacent risk in its own right (cross-reference [Platforms-Hardware](../Platforms-Hardware/README.md) EOS guidance) — the migration itself is the remediation.
- **XCP** (also applies here — see heterogeneous section below, since XCP is explicitly "any-to-NetApp **and** NetApp-to-NetApp") — the right choice for **NAS-level, file-based** homogeneous migration (e.g., consolidating multiple old NetApp NAS volumes into new AFF/ASA/AFX capacity) where a block-level `volume move`/SnapMirror approach isn't the right fit (e.g., re-laying-out qtree/share structure along the way).

## Storage-based, heterogeneous (3rd-party → NetApp)

- **Foreign LUN Import (FLI)** — block-level only. [FLI documentation hub](https://docs.netapp.com/us-en/ontap-fli/) · [FLI overview](https://docs.netapp.com/us-en/ontap-fli/san-migration/concept_foreign_lun_import_overview.html) · [Data Migration Tools Quick Reference (PDF — covers file-protocol migration options FLI doesn't address)](https://library.netapp.com/ecm/ecm_get_file/ECMP12363719) · [FLI concepts](https://docs.netapp.com/us-en/ontap-fli/san-migration/concept_foreign_lun_import_concepts.html) · [Migration types supported by FLI](https://docs.netapp.com/us-en/ontap-fli/san-migration/concept_migration_types_supported_by_foreign_lun_import.html) · [LUN requirements and limitations](https://docs.netapp.com/us-en/ontap-fli/san-migration/concept_lun_requirements_and_limitations.html) · [Using FLI to import LUNs into All Flash (AFF)](https://docs.netapp.com/us-en/ontap-fli/san-migration/concept_using_fli_to_import_luns_into_all_flash.html)
  - Built into ONTAP; imports LUNs from **EMC, Hitachi, HP, and other supported foreign arrays** directly into ONTAP LUNs.
  - **FC connections only** — no iSCSI source support; requires at least one physical FC port per controller, with LUNs migrated directly in **Initiator mode**.
  - **Strictly block-level** — no file, NFS, or CIFS/SMB migration capability; the foreign LUN and the destination ONTAP LUN must both use **512-byte block size**. For file-protocol migrations, NetApp's own FLI documentation points to the separate [Data Migration Tools Quick Reference](https://library.netapp.com/ecm/ecm_get_file/ECMP12363719) rather than FLI — use XCP (below) for that instead.
  - NetApp's official guidance: **professional services involvement is no longer a hard requirement** for FLI, but NetApp still **strongly recommends PS involvement in scoping, planning, and training** for all but the simplest migrations — worth citing directly when a customer questions why PS is being engaged for "just a LUN migration."
  - **Two migration types**: **offline** (source disrupted/unavailable for the duration of the import — full outage) and **online** (mainly non-disruptive, but still requires careful source-LUN mapping/path management — see [prepare foreign array LUNs for offline migration](https://docs.netapp.com/us-en/ontap-fli/san-migration/prepare-foreign-lun-offline.html) and [map the source LUN for online migration](https://docs.netapp.com/us-en/ontap-fli/san-migration/map-source-lun-to-destination-online-migration.html)).
  - **Risk note**: classify **offline FLI as destructive-tier from an availability standpoint** even though no data is lost — it is a planned full outage of the source LUN for the migration window, and must be scheduled/communicated as such. Online FLI is disruptive-but-safe-tier — confirm multipathing/zoning is correctly staged on both source and destination before cutover, since a botched path cutover mid-migration is where "non-disruptive" online FLI turns into an outage.
- **NetApp XCP** — file/NAS-level, any-NAS-to-NetApp (and NetApp-to-NetApp). [XCP documentation hub](https://docs.netapp.com/us-en/xcp/) · [XCP overview/best practices](https://docs.netapp.com/us-en/netapp-solutions-dataops/xcp/xcp-bp-netapp-xcp-overview.html) · [Migration workflow overview](https://docs.netapp.com/us-en/netapp-solutions/xcp/xcp-bp-migration-workflow-overview.html) · [Plan NFS data migration](https://docs.netapp.com/us-en/xcp/xcp-plan-nfs-data-migration.html) · [Migrate NFS data](https://docs.netapp.com/us-en/xcp/xcp-migrate-data.html) · [Migrate SMB data](https://docs.netapp.com/us-en/xcp/xcp-migrate-smb-data.html) · [Deployment steps](https://docs.netapp.com/us-en/netapp-solutions-dataops/xcp/xcp-bp-deployment-steps.html) · [XCP license management portal](https://xcp.netapp.com/)
  - Client-based software tool, high-performance, protocol-level (NFS and SMB) — works against **any source NAS**, not just NetApp, into NetApp NAS.
  - Four operations: **scan** (discover/report source layout), **copy** (initial transfer — files, hard links, symlinks, special file types, permissions, ownership, NTFS ACLs preserved), **sync** (incremental — finds and applies only what changed since the last copy/sync, minimizing final cutover time), **verify** (full or selective byte-level comparison, including ACLs/attributes, post-sync).
  - Standard workflow: discover shares → scan/report → initial copy → iterative sync passes (shrinking the remaining delta) → final short-window sync + verify → cutover (redirect clients to the new NetApp NAS target).
  - **Risk note**: XCP's incremental-sync design exists specifically to make the **final cutover window short and low-risk** rather than a single large disruptive copy — don't shortcut the iterative-sync phase to save time; skipping it turns a low-risk migration into a long, disruptive one.
  - **Current version confirmed via direct fetch 2026-08-08, re-confirmed 2026-09-14**: [XCP v1.9.4P1 Release Notes](https://docs.netapp.com/us-en/xcp/releasenotes.html) page title/heading confirms **v1.9.4P1 is still the current release** (page dated 06/27/2025, byte-for-byte unchanged across both checks) — this resolves a previously unconfirmed version lead.
- **BlueXP Copy and Sync (formerly Cloud Sync)** — NAS ↔ object, cross-cloud/cross-vendor. [Copy and Sync documentation hub](https://docs.netapp.com/us-en/bluexp-copy-sync/) · [Concept overview](https://docs.netapp.com/us-en/data-services-copy-sync/concept-cloud-sync.html) · [Technical FAQ](https://docs.netapp.com/us-en/bluexp-copy-sync/faq.html)
  - SaaS platform; a **data broker** (deployable in AWS, Azure, GCP, or on-prem) performs the actual sync between a source and target — source/target can be file-based NAS (NFS/SMB), Amazon S3, a NetApp StorageGRID appliance, or another cloud provider's object store, with format conversion (file↔object) handled automatically.
  - After the initial copy, only **changed data** is synced on the configured schedule — efficient for ongoing replication/migration rather than a one-shot copy tool; transport is TLS 1.3-encrypted.
  - Best fit: migrating or continuously syncing NAS data into/out of cloud object storage (including cross-vendor, e.g., a competitor's NAS into StorageGRID or S3-behind-ONTAP) where XCP's NFS/SMB-to-NFS/SMB model doesn't apply because the target is object storage.

## Application-based migration

- **VM migration — NetApp Shift Toolkit**: free, standalone cross-hypervisor VM migration tool. [Shift Toolkit overview](https://docs.netapp.com/us-en/netapp-solutions-virtualization/migration/shift-toolkit-overview.html) · [Migrate VMs using the Shift Toolkit](https://docs.netapp.com/us-en/netapp-solutions-virtualization/migration/shift-toolkit-migration.html) · [Migrate VMs from Hyper-V to ESXi](https://docs.netapp.com/us-en/netapp-solutions-virtualization/migration/shift-toolkit-migrate-hyperv2esxi.html) · [Migrate VMs from SAN environments for conversion](https://docs.netapp.com/us-en/netapp-solutions-virtualization/migration/shift-toolkit-san.html) · [Next steps after converting/migrating](https://docs.netapp.com/us-en/netapp-solutions-virtualization/migration/shift-toolkit-summary.html) · [OpenShift Virtualization migration path](https://community.netapp.com/t5/Tech-ONTAP-Blogs/Move-Your-VMs-to-OpenShift-Virtualization-The-Shift-Toolkit-Way/ba-p/462579)
  - Supports migration across ESXi, Hyper-V, Red Hat/Oracle Linux Virtualization Manager (RHV/OLVM), OpenShift Virtualization, and — **added 2026-07-18, direct-fetch confirmed** — **Proxmox VE**.
  - **KVM-variant support and VMware↔Hyper-V bidirectional migration — confirmed via direct fetch 2026-08-08** ([NetApp Shift Toolkit: Maximize hypervisor flexibility](https://www.netapp.com/product-updates/shift-toolkit-hypervisor-flexibility/), NetApp product-updates page dated 2025-10-14). This resolves a previously unconfirmed lead: the page's own wording, quoted directly, states the Shift Toolkit "gives customers the ability to migrate to KVM variants like Red Hat OpenShift Virtualization, Proxmox, Oracle Linux VM, and more... and it enables **bidirectional migration for VMware and Hyper-V**."   - **ESXi → Proxmox VE (new, added 2026-07-18)**: [Migrate VMs from VMware ESXi to Proxmox VE using the Shift Toolkit](https://docs.netapp.com/us-en/netapp-solutions-virtualization/migration/shift-toolkit-migrate-esxi2proxmox.html) (direct-fetched, dated 07/02/2026 — the newest-dated Shift Toolkit page found in this library). Requires an operational 3+ node Proxmox VE 9.x+ cluster with quorum and ONTAP NFSv3 storage added as a pool; converts VMDK to QCOW2 (or RAW) at the volume level via the same disk-format-conversion mechanism as the other hypervisor pairs (FlexClone-backed, seconds not hours). See [Hypervisors — Proxmox VE](../Hypervisors/README.md#proxmox-virtual-environment-ve) for the broader Proxmox/ONTAP storage-integration context (Storage Manager for Proxmox, Proxmox Backup Server) this migration path feeds into.
  - Mechanism: uses **FlexClone** to convert VM disk formats between hypervisors near-instantly (no full data copy) — a 1TB VMDK-equivalent conversion that would otherwise take hours completes in seconds because FlexClone clones at the storage layer rather than copying bytes.
  - **SAN-sourced VMs**: Shift Toolkit currently operates against **NAS datastores** — a VM currently on a SAN (VMFS/block) datastore is first moved to an NFS datastore via **VMware Storage vMotion** (non-disruptive, no VM downtime) as a prerequisite step, then Shift Toolkit performs the cross-hypervisor conversion from there.
  - Migration phases: Prepare (verify prerequisites) → Migrate and validate (convert/present to target hypervisor) → Test (validate the converted VM boots and functions correctly on the target) before final cutover.

- **Database migration**: primarily accomplished via **SnapCenter** application-consistent clone/snapshot workflows rather than a dedicated "migration tool" — see [Data-Protection/README.md — SnapCenter](../Data-Protection/README.md#snapcenter) for plug-in-specific (Oracle, SQL Server, MySQL, SAP HANA) storage-prep and snapshot mechanics, which are the same mechanics used to stand up a migrated/cloned copy of a database on new storage.
- **Kubernetes storage-class / PV migration**: **Astra Control** storage-class migration moves an application's persistent volumes to a different StorageClass/backend without an application-level export/import — see [Kubernetes-Containers — Advanced Astra Control workflows](../Kubernetes-Containers/README.md#advanced-astra-control-workflows).

## Choosing the right tool — quick reference
- Moving a volume within a cluster (rebalance, decommission a node/aggregate): **`volume move`**.
- Moving NetApp data to a different NetApp cluster/site, homogeneous, block or NAS: **SnapMirror-based migration**.
- Still running 7-Mode: **7MTT Copy-Based Transition** (don't attempt to hand-roll this with generic SnapMirror — 7MTT handles the 7-Mode-specific mechanics).
- Migrating LUNs off a competitor's block array (EMC/Hitachi/HP/etc.) into ONTAP: **Foreign LUN Import**, understanding the FC-only, block-only, offline-vs-online tradeoffs above.
- Migrating file shares from any vendor's NAS (or another NetApp system) into NetApp NAS: **XCP**.
- Migrating or continuously syncing NAS data into/out of cloud object storage, or across cloud providers: **BlueXP Copy and Sync**.
- Converting/moving VMs across hypervisors (ESXi, Hyper-V, RHV/OLVM, OpenShift Virtualization, Proxmox VE): **Shift Toolkit** (via Storage vMotion first if the source is SAN-based).
- Migrating a database to new storage with application consistency: **SnapCenter**-driven clone/restore workflow, not a generic file-copy tool.
- Moving Kubernetes-persistent-volume-backed apps to a new backend: **Astra Control** storage-class migration.
