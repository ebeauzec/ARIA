- Integration mechanism: Varonis (and similar FPolicy-consuming DSPM tools) registers as an ONTAP **FPolicy** external engine — it receives real-time file-access event notifications (and can enforce screening/blocking policies) over CIFS/NFS without agents on the storage controller itself.
- Architecture note: FPolicy is a real-time event-notification framework, not a scan-on-schedule mechanism — a DSPM platform can use it for continuous access monitoring (feeding its behavioral/DDR engine) in addition to periodic content-classification crawls. Confirm FPolicy server sizing and network path before enabling on a high-IOPS SVM — a misbehaving or overloaded FPolicy engine can add client-visible latency (see [Risk & disruption notes](#risk--disruption-notes) below).

## Risk & disruption notes
- Enabling a new **FPolicy** engine or a native scan job against a production SVM is generally **non-disruptive** when properly sized, but a misconfigured synchronous FPolicy policy (one that blocks I/O pending an external engine's response) can turn a DSPM tool outage into a client-facing storage outage — always confirm whether the policy mode is synchronous (blocking) or asynchronous (notify-only) before enabling it on a production SVM, per the [Operating Protocol](../OPERATING-PROTOCOL.md).
- A first-time full classification/DSPM scan across a large existing NAS estate is a **read-heavy bulk operation** — schedule it like any other bulk read workload (off-peak, or throttled) rather than assuming it's free; it can compete with production workload for controller CPU/read IOPS on the same aggregate.
- DSPM findings that trigger automated remediation (auto-quarantine, auto-permission-lockdown) should be treated as **disruptive-tier** actions in their own right — confirm the remediation won't cut off legitimate application access before enabling "auto-remediate" modes rather than "alert only."
