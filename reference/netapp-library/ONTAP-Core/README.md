## Storage virtualization: FlexClone, FlexCache, FlexGroup
**New section, added 2026-07-11** — these three FlexVol-derived technologies are foundational to migration ([Shift Toolkit's use of FlexClone](../Migration/README.md#application-based-migration)), Kubernetes/database cloning workflows, and cache-driven distributed-access designs, but weren't previously indexed with their own reference links.
- **FlexClone** — [How FlexClone volumes work with FlexClone files and FlexClone LUNs](https://docs.netapp.com/us-en/ontap/volumes/flexclone-volumes-files-luns-concept.html) · [FlexClone volume use overview](https://docs.netapp.com/us-en/ontap/volumes/flexclone-efficient-copies-concept.html) · [Reasons for using FlexClone LUNs](https://docs.netapp.com/us-en/ontap/san-admin/reasons-cloning-luns-concept.html) · [How an HA configuration works with FlexClone files and LUNs](https://docs.netapp.com/us-en/ontap/volumes/ha-pair-flexclone-files-luns-concept.html). Writable, point-in-time copies of a parent FlexVol that share data blocks with the parent (space-efficient — only diverging writes consume new capacity). This is the underlying mechanism behind Shift Toolkit's near-instant VM disk-format conversion and is commonly used for database dev/test clone-and-refresh workflows via SnapCenter.
- **FlexGroup** — [Learn about ONTAP FlexGroup volumes](https://docs.netapp.com/us-en/ontap/flexgroup/definition-concept.html) · [FlexGroup volumes (cloud context)](https://docs.netapp.com/us-en/ontap/cloud/flexgroup-volumes-concept.html). A scale-out NAS container composed of multiple member volumes (constituents) that automatically and transparently distribute traffic/capacity across nodes — built for near-infinite capacity plus predictable low latency in metadata-heavy workloads (e.g., large user/engineering home-directory or AI/ML training-data shares). Relevant cross-reference: [Platforms-Hardware — AFX](../Platforms-Hardware/README.md#afx--disaggregated-ontap-for-ai-scale-workloads) documents AFX's constituent-volumes-per-FlexGroup ceiling specifically.
- **FlexCache** — [Create ONTAP FlexCache volumes](https://docs.netapp.com/us-en/ontap/flexcache/create-volume-task.html) · [ONTAP FlexCache and FlexGroup technical reports](https://docs.netapp.com/us-en/ontap-technical-reports/nas-containers.html). A sparse, read-and-write-capable cache of an origin FlexVol/FlexGroup volume at a remote location — since ONTAP 9.7, both FlexVol and FlexGroup volumes are supported as origins, and FlexCache requires no separate license. **Write-back mode** commits a write to the cache immediately (acknowledged to the client without waiting for the origin) and asynchronously flushes it back — enables near-local write latency for a globally distributed filesystem, but note [Platforms-Hardware — AFX](../Platforms-Hardware/README.md#afx--disaggregated-ontap-for-ai-scale-workloads) already flags that AFX does not support FlexCache write-back as either an origin or target.

## Cluster & SVM peering
**New section, added 2026-07-11.** [Learn about ONTAP cluster and SVM peering](https://docs.netapp.com/us-en/ontap/peering/) · [Peering basics](https://docs.netapp.com/us-en/ontap/peering/peering-basics-concept.html) · [Create cluster peer relationships](https://docs.netapp.com/us-en/ontap/peering/create-cluster-relationship-93-later-task.html) · [Create intercluster SVM peer relationships](https://docs.netapp.com/us-en/ontap/peering/create-intercluster-svm-peer-relationship-93-later-task.html) · [Add SVM intercluster relationships](https://docs.netapp.com/us-en/ontap/peering/add-svm-intercluster-relationship-93-later-task.html). This is the prerequisite plumbing for every cross-cluster SnapMirror relationship documented in [Data-Protection](../Data-Protection/README.md) and every SnapMirror-based migration in [Migration](../Migration/README.md) — worth a dedicated reference rather than assuming it as background knowledge.
- **Cluster peering**: establishes the secure network relationship (over dedicated intercluster LIFs, created on every node in both clusters) that must exist before any cross-cluster SnapMirror/SnapVault relationship can be created.
- **SVM peering**: layered on top of an established cluster peer relationship — the source cluster's SVM must be "pre-authorized" to peer with a specific SVM on the remote/peered cluster before a data-protection relationship targeting that SVM can be created.
- **Sequencing note**: cluster peering must exist first; SVM peering (and, in turn, any SnapMirror relationship between the two SVMs) cannot be established without it. When a customer's SnapMirror setup is failing at the relationship-creation step, verify both peering layers independently before troubleshooting SnapMirror itself — a broken or never-established peer relationship is a common root cause easily mistaken for a SnapMirror-specific problem.

## Upgrades
**New section, added 2026-07-11.** [Learn about ONTAP upgrade](https://docs.netapp.com/us-en/ontap/upgrade/) · [Supported ONTAP upgrade paths](https://docs.netapp.com/us-en/ontap/upgrade/concept_upgrade_paths.html) · [ONTAP software upgrade methods](https://docs.netapp.com/us-en/ontap/upgrade/concept_upgrade_methods.html) · [Install the ONTAP image with automated nondisruptive upgrade (ANDU)](https://docs.netapp.com/us-en/ontap/upgrade/automated-upgrade-task.html) · [Manual nondisruptive upgrade via CLI](https://docs.netapp.com/us-en/ontap/upgrade/task_upgrade_nondisruptive_manual_cli.html).
- **ANDU (Automated Nondisruptive Upgrade)** is NetApp's recommended default method — it drives the same HA-failover mechanism as a manual takeover/giveback sequence but sequences and validates it automatically; System Manager is the recommended front-end for triggering it unless the target configuration requires the manual CLI path.
- **Upgrade paths** (direct, direct multi-hop, or multi-stage) depend on the current and target ONTAP versions and the hardware platform — always resolve the exact path via the official upgrade-paths tool/page rather than assuming any two GA versions can be jumped directly; an unsupported multi-hop attempt is the kind of mistake that turns a routine upgrade into an outage.
- **Risk classification**: per the [Operating Protocol](../OPERATING-PROTOCOL.md), an ONTAP upgrade — automated or manual — is **disruptive-but-safe when pre-conditions hold**: confirm HA health (`storage failover show`), absence of any existing degraded/takeover-state node, and a validated upgrade path before starting, exactly like any other HA-failover-dependent procedure in this library.
- **Known ANDU giveback failure — 9.16.1P1 to 9.19.1 (added 2026-10-08, direct-fetch confirmed)**: [CONTAP-799924](https://kb.netapp.com/on-prem/ontap/OHW/OHW-Issues/CONTAP-799924) (published 2026-09-22; duplicate tracker [CHW-3959](https://kb.netapp.com/on-prem/ontap/OHW/OHW-Issues/CHW-3959), updated 2026-10-08). Public summary: during a rolling upgrade from 9.16.1P1 to 9.19.1, the taken-over node reached "Waiting for Giveback", the serving node reported a WAFL/RAID HA RDMA QP reject (code 38), and NFO shut the returning node down. Repeated giveback attempts sent the node back to "Waiting for Giveback". The fix and workaround are behind the KB login. **Risk note**: the HA pair stays in takeover, so it has **no redundancy** until the giveback succeeds. If giveback fails during ANDU, **do not keep retrying the giveback**: stop, leave the pair in takeover (it is still serving data), collect AutoSupport, and open a case. Plan the maintenance window so it can absorb a node that stays down.

## Risk & disruption notes (applies across all ONTAP CLI guidance — see [OPERATING-PROTOCOL.md](../OPERATING-PROTOCOL.md))
- **Destructive/irreversible command classes** to always flag explicitly before recommending, and never present as the default option without stating the alternative: `volume delete`, `storage aggregate delete`, `storage aggregate offline` (state-changing, not deletion, but stops all volume access on that aggregate), `lun delete`, `volume snapshot delete`/`volume snapshot policy delete`, `storage encryption disk destroy`/`sanitize`/`revert-to-original-state`, `volume file privileged-delete`, `system node systemshell`/`system node run` (bypass ONTAP's normal safeguards), and any command run with a `-force` flag that suppresses a confirmation prompt.
- Most of the commands above are Multi-Admin Verification (MAV) rule-protected by default from ONTAP 9.11.1+ (see [Security-Hardening](../Security-Hardening/README.md#multi-admin-verification-mav)) — if MAV is enabled on the target cluster, factor the second-approver step into timing and don't assume a single administrator can complete the change unassisted.
- **Disruptive-but-safe command classes** (require confirming HA/redundancy state first, per the Operating Protocol): `storage failover takeover`/`giveback`, non-disruptive upgrade (NDU) procedures, node reboot/halt, cluster switch firmware upgrade. Confirm `storage failover show` / `cluster show` health before recommending any of these.
- Read-only/reporting commands (`show`, `check run` in report mode, `stats`, `qos statistics ... show`) are always safe to recommend first when diagnosing an issue — lead with these before any state-changing command.
