# ONTAP 9.x Feature & CLI-Behavior Version History

Companion to [ONTAP-Core/README.md](README.md) — that page covers the current command-reference links; this file tracks what materially changed release-to-release (9.8 through the current 9.19.1 GA) so a version-pinned recommendation can be sanity-checked against what actually shipped when. Read [OPERATING-PROTOCOL.md](../OPERATING-PROTOCOL.md) first: matching the target system's real version to the behavior described here is exactly the "verify before recommending" requirement, and several of the CLI changes below (LIF admin-down confirmation, firewall-policy deprecation) will break a script or runbook written against an older release if not accounted for.

**Sourcing**: every row below is drawn from NetApp's own `docs.netapp.com/us-en/ontap/release-notes/whats-new-*.html` pages, directly fetched and verified on 2026-07-09 (9.10.1, 9.12.1, 9.14.1, 9.16.1) or already verified in [ONTAP-Core/README.md](README.md) (9.19.1). Versions not directly fetched this pass (9.9.1, 9.11.1, 9.13.1, 9.15.1, 9.17.1, 9.18.1) are covered only where another primary source (the MetroCluster "what's new" page, fetched 2026-07-09) independently confirmed a feature landing in that release — do not treat this file as a complete substitute for the authenticated ONTAP 9 Release Notes PDF (`library.netapp.com/ecm/ecm_download_file/ECMLP2492508`, login required), which is the only authoritative source for upgrade cautions and known issues per release.

## Why this matters for command syntax specifically

ONTAP's CLI is generally additive and backward-compatible within the 9.x line, but a small number of releases changed default behavior or removed a mechanism outright — these are the ones worth checking before assuming a script written years ago still behaves identically:

- **ONTAP 9.10.1 — firewall policies deprecated, replaced by LIF service policies.** Any automation still referencing the old `system services firewall policy` construct needs updating to `network interface service-policy` — NetApp's own release note is explicit that this is a breaking change for scripts, not just a preferred-practice shift.
- **ONTAP 9.10.1 — confirmation required before setting `status admin` to `down` on a LIF in a system SVM.** A scripted `network interface modify -status-admin down` against a system-SVM LIF that worked non-interactively pre-9.10.1 will now prompt for confirmation (or need a `-force`/confirm flag threaded through) — NetApp flags this explicitly as something that "must update" scripts invoking this at the CLI.
- **ONTAP 9.12.1 — `volume rebalance file-move` becomes the documented mechanism** for FlexGroup member-volume rebalancing after a FlexVol→FlexGroup conversion, explicitly recommended over relying on automatic rebalancing in that specific post-conversion scenario.
- **ONTAP 9.14.1 — `volume show -physical-used` / `volume show-space -physical-used` semantics change** on TSSE-enabled volumes: the reported physical-used figure now includes TSSE space savings, which will shift capacity-reporting baselines for any monitoring/alerting built against the raw metric from an earlier release.
- **ONTAP 9.14.1 — CLI support added for consistency groups** (introduced as a concept in 9.10.1, System Manager/REST-only at first) — 9.10.1-era consistency-group automation that assumed REST-API-only management should be revisited once a cluster is on 9.14.1+.

## SnapMirror Synchronous — the two policy types, clarified

Not a version change, but a frequently-confused piece of command syntax worth stating precisely (verified 2026-07-09 against `docs.netapp.com/us-en/ontap/data-protection/workloads-strictsync-sync-policies-concept.html`, correcting an internal assumption checked before publishing rather than asserted): SnapMirror Synchronous (available since ONTAP 9.5, FAS/AFF with 16GB+ RAM, SnapMirror-license-gated) is configured with one of two policy types, not a single "sync mode" —

- **`sync-mirror` policy**: if the relationship goes `OutOfSync` (e.g., a transient replication failure), primary-volume I/O **continues uninterrupted** — non-disruptive but the destination falls behind until resync.
- **`strict-sync-mirror` policy**: if the relationship goes `OutOfSync`, primary-volume I/O is **stopped** until the relationship is restored — enforces zero-RPO at the cost of availability.

Neither policy type is deprecated as of this check; both remain current. This distinction is the one to confirm explicitly before recommending SnapMirror Synchronous for a workload — `strict-sync-mirror` is a deliberate availability-for-consistency tradeoff, not a "stricter is safer" default, and should be classified as a design decision under the [Operating Protocol](../OPERATING-PROTOCOL.md#2-classify-every-recommended-action-before-giving-steps) rather than assumed.
